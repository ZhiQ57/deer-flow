# TableRAG 业务数据查询协作

## 目标与边界

本 Skill 用于帮助模型处理需要真实业务数据支撑的问题，例如指标查询、明细查询、趋势分析、排名、对比和多表关联查询。它提供判断依据与协作边界，不规定一条固定的调用流水线。

模型应根据当前用户问题、已有对话、历史工具结果、运行时状态和可用工具能力，自主判断下一步是：

- 直接回答；
- 补充 Schema、业务口径、字段值或关联关系信息；
- 向用户提出一个会实质影响结果的澄清问题；
- 将查询目标或候选 SQL 交给当前可用的 SQL 工具路由 / Tool Use 能力；
- 读取并解释查询结果；
- 根据错误、空结果或用户修正重新评估；
- 说明缺少的能力或证据。

普通问候、通用 SQL 语法讲解、与业务数据无关的问题，以及数据库管理类操作，不应因为本 Skill 被强行转成 TableRAG 或 SQL 流程。

## 自主决策原则

不要为了满足预设顺序而调用工具，也不要为了省略步骤而凭空补全事实。每次行动前，判断当前上下文是否足以支持下一步：

- 如果表、字段、业务术语、真实字段值或 Join 关系未知，且它们会影响答案，应使用当前可用的 TableRAG、Schema 或业务语义检索能力。
- 如果已有可靠的检索结果或历史上下文足以支撑查询，不要重复检索；只有在新问题、新约束或现有证据不足时才补充。
- 如果存在多个会产生不同 SQL 或不同结论的解释，应澄清或使用运行时提供的确认能力；能够从用户原话、已确认上下文或可靠证据推断的内容，不要无故打断用户。
- 如果用户需要真实数据，应优先协作完成查询，而不是只给出一段未经验证的 SQL 教程代码。
- 如果查询已经执行，应先判断结果是否真正回答了用户问题，再决定是解释、继续处理、修正查询还是报告限制。
- 如果工具不可用、结果不足或权限不允许，应如实说明当前阻塞点，不要声称已经检索、校验或执行成功。

## 数据与证据

处理业务查询时，保持以下信息之间的区别：

- 用户明确提出的指标、维度、筛选条件、时间范围、排序、粒度和输出形式；
- TableRAG 或其他可信工具返回的业务定义、表、字段、字段值和关联证据；
- 模型根据上下文推导出的解释或假设。

使用检索能力时，应围绕当前问题保留完整语义，不要丢失时间范围、比较对象、过滤条件、聚合粒度或输出要求。检索结果应作为查询决策和 SQL 约束的依据，但低置信度、冲突或明显不完整的结果不能被当作确定事实。

不得编造不存在的表、字段、字段值、业务口径、Join 条件或查询结果。若当前运行时返回结构化 Evidence、引用、来源或其他标识，应在后续协作和最终说明中尽量保留其关联关系；不得伪造、篡改或把自由文本包装成工具证据。

## 与工具路由和 Tool Use 协作

SQL 的生成、校验、执行和结果获取由当前运行时提供的工具路由能力承接。这里不固化系统路由层、MCP Server、子代理、工具名称、参数格式、内部状态字段或调用次数；未来切换为 Tool Use 或其他实现时，Skill 仍应保持有效。

需要调用工具时，应以当前实际可用工具及其 Schema 为准，再决定需要提供什么信息。根据工具接口的要求，可以提交：

- 用户的查询目标和结构化约束；
- 经证据支持的表、字段、字段值、Join 和业务口径；
- 候选 SQL 或 SQL 生成所需的上下文；
- 对错误、空结果、结果异常或用户修正的处理意图。

是否需要先检索、是否需要澄清、是否需要生成候选 SQL、是否直接调用高层 SQL 能力，以及是否需要再次处理，应由模型结合当前上下文和工具反馈自主判断。不要假设某个固定工具一定存在，也不要调用未出现在当前工具列表或工具 Schema 中的能力。

SQL 工具返回的结构化结果、校验结果和执行结果是事实依据。工具调用本身不等于执行成功；只有看到明确的成功结果，才能向用户报告查询已完成。工具错误、权限限制、超时、空结果和业务上确实没有匹配数据，应分别说明，不要混为一谈。

除非运行时明确提供并授权其他能力，本 Skill 默认只协作只读业务查询。不得绕过已提供的工具路由直接连接数据库、索取或泄露 DSN、Secret、内部连接信息，也不得通过 SQL 或文件操作修改数据或数据库结构。

## 查询质量与安全边界

- 查询必须尽量忠实表达用户的业务意图，不为得到更“好看”的结果而擅自改变筛选条件、时间范围、聚合粒度或排序规则。
- 需要多表查询时，使用当前可信上下文或工具确认的关联关系；不凭经验猜测 Join。
- 用户要求明细时，结合运行时限制控制返回规模；不要在不了解限制的情况下承诺完整导出全部数据。
- 只读查询默认不包含 `INSERT`、`UPDATE`、`DELETE`、`MERGE`、`TRUNCATE`、`DROP`、`ALTER`、`CREATE`、事务控制、锁表、文件写入或多语句操作。
- 不把内部快照、注册表、校验摘要、路由细节或数据库连接信息当作用户答案的必要内容；只有在工具结果或排障需求确实需要时才说明。
- 任何敏感数据都应遵循当前运行时的权限、脱敏和输出限制。

## 处理不确定性、错误和用户修正

当用户的补充说明改变了指标口径、筛选条件、时间范围、字段值、关联关系或输出要求时，将其作为新的约束重新评估当前查询。过期的假设、候选 SQL、校验结果和执行结果不能继续被当作新结论的依据。

遇到错误、空结果或与用户预期明显不符时，先根据错误信息和已有证据判断原因，再选择最小必要动作：修正查询、补充检索、请求澄清、重新交给 SQL 工具，或直接解释“没有匹配数据”。不要无目的重复调用，也不要为了迎合预期数值而修改业务含义。

如果关键信息无法从用户表达、已有上下文或可用工具中可靠获得，应明确指出缺失项，并提出一个聚焦、可回答的问题。无法继续时，给出已经确认的内容、尚未确认的内容和下一步所需能力。

## 输出建议

最终回答按用户需要保持简洁，但应让用户能够理解结论的依据。适合时包含：

1. 对问题的简短理解；
2. 关键业务口径、筛选条件、时间范围、表字段或 Evidence 摘要；
3. 查询结果和直接结论；
4. 实际使用的 SQL 或查询说明（工具结果和用户需求适合展示时）；
5. 重要假设、数据限制、空结果或失败原因；
6. 如果用户后来修正了条件，说明新约束如何影响查询和结论。

不要为了形式完整而展示内部路由流程，也不要把尚未得到工具确认的推测写成已执行结果。
