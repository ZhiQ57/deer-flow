# 开源实现参考与设计启发

## 医疗聊天与症状检查类

1. MedChat-AI
   - 启发：医疗聊天应用需要面向健康咨询、症状分析、上下文响应和可靠知识来源。
   - 本 Skill 的取舍：保留“上下文问答”和“症状采集”的思路，但不输出最终诊断或治疗方案。

2. Medi_Bud
   - 启发：医疗聊天可以结合 RAG、记忆、文档上传和处方/报告解释。
   - 本 Skill 的取舍：支持上传报告摘要进入病历，但强调报告解释需医生复核。

3. Doctor-Chatbot
   - 启发：多 Agent、专科角色、报告上传、体征/检查建议等设计适合复杂医疗助手。
   - 本 Skill 的取舍：只保留“角色化问诊”和“结构化信息采集”，不实现自动诊断、开药或检查医嘱。

4. Symptom-Checker 与 Symptom-Checker-Chatbot
   - 启发：症状可以通过表单、是/否问题和交互式追问收集。
   - 本 Skill 的取舍：避免固定长表单，采用动态追问并保留关键阴性症状。

## 角色扮演与引导对话类

1. Talemate
   - 启发：角色、场景、长期上下文和状态管理会显著影响对话一致性。
   - 本 Skill 的取舍：将“医生/护士式角色”限制在问诊采集，不扮演真实执业身份。

2. AutoGRAMS
   - 启发：对话可以作为有状态程序运行，变量和分支会随用户回答变化。
   - 本 Skill 的取舍：将问诊状态抽象为主诉、红旗、HPI、既往史、缺失字段，而不是固定问卷流程。

3. Agent Squad
   - 启发：复杂对话可以通过意图分类和不同 Agent 路由处理。
   - 本 Skill 的取舍：使用“模式切换”而不是多 Agent 运行，包括普通预问诊、红旗急诊摘要、报告整理、JSON 输出等。

## 医疗结构化表单与 FHIR 类

1. Smart Forms
   - 启发：FHIR Questionnaire 和 QuestionnaireResponse 适合标准化采集健康问卷和临床表单。
   - 本 Skill 的取舍：默认输出中文病历，也提供 FHIR 映射思路，便于后续系统集成。

2. lforms-fhir-app
   - 启发：FHIR 表单渲染和 QuestionnaireResponse 可以与 SMART on FHIR/EHR 场景结合。
   - 本 Skill 的取舍：不直接连接 EHR，但保留字段稳定性和问答顺序，方便未来对接。

## 设计结论

本 Skill 不做“诊断机器人”，而做“临床问诊采集与结构化病历生成器”。核心价值是：

- 动态追问，而不是固定问卷；
- 角色化沟通，而不是冒充医生；
- 红旗优先，而不是追求问诊完整；
- 结构化输出，而不是只给自然语言建议；
- 可接入 FHIR，但不把模型推断伪装成正式临床诊断。
