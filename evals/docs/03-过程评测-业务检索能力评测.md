# 过程评测 - 业务检索能力评测
仅使用端到端结果评分，难以区分意图理解、业务检索、SQL 生成等环节的错误。因此增加模块级评测和轨迹检查，以支持错误定位及组件优化。本方案单独评测 Agent「是否该检索、如何检索、如何使用结果、何时补检、何时停止」的能力。
> 初始阶段无法概括所有用例, 后续继续补充.

当前方案拆为两个独立文档，分别维护数据集、指标和执行设计：

- [业务检索能力评测 - 意图前](05-评测体系-过程评测-业务检索能力评测-意图前.md)：使用网络搜索、内部知识检索、MCP 或其他授权工具，为意图识别取得业务知识。
- [业务检索能力评测 - 意图后](05-评测体系-过程评测-业务检索能力评测-意图后.md)：基于已发布意图，通过 MCP 获取 SQL 与答案所需的必要 Schema 及业务依据。

本文件保留拆分说明与初版记录。两套 Benchmark 的当前执行规范以对应独立文档为准。

## 1.评测目标与范围

DataAgent 的业务检索发生在两个不同位置：意图识别前，通过业务概念、术语、指标口径和背景资料帮助理解用户需求；意图呈现后，通过 MCP 获取必要 Schema、字段、关联关系及业务值映射，为更准确的 SQL 和答案准备依据。两者的输入、工具范围和成功标准不同，因此在本方案中建立两套独立 Benchmark，分别支持 System Prompt、Skill、工具定义及检索策略的版本迭代。

核心参考通用 Agent 五大评测维度（功能正确性、过程质量、效率与成本、鲁棒性与安全、体验与对齐），结合两个检索阶段的职责，设计相应评测项和评价指标。

本方案的评测边界：

- 共同评：检索调用决策、查询构造、结果理解与选择、证据采用、补充检索、上下文复用、停止及异常恢复。
- 意图前评测：从原始问题和当时可见历史出发，使用已配置的网络搜索、内部知识检索、文件工具、MCP 或其他授权工具，交接支撑意图识别的业务知识与未解决问题。不能预填本轮标准意图。
- 意图后评测：从已发布的冻结意图与当时已确认条件出发，通过 MCP 取得 SQL 和答案所需的业务依据。单体主集使用经核对的上游意图，隔离意图识别错误。
- 两阶段发现阻断性歧义时，检查是否正确交接给澄清环节；具体追问质量由歧义澄清方案负责。意图槽位提取和标签发布正确性由意图识别方案负责。
- 下游 SQL 的生成、执行、结果解释和最终答案正确性由对应过程或端到端评测负责，不直接当作本方案的主分数。
- MCP Server 的单次召回率、内部排序、检索通道消融和服务性能，由 [SQL Schema Recall 评测](<05-评测体系-过程评测-SQL Schema Recall 评测.md>) 负责。

**两套评测的职责划分**

```csv
对比项,意图前业务知识检索,意图后 MCP Schema 检索
阶段标识,pre_intent,post_intent
目的,帮助更准确理解用户要查什么,为已发布需求找到生成 SQL 和回答所需的必要依据
输入起点,原始问题及发布当前意图前已可见的历史,已发布的冻结意图及当时有效的检索历史
检索对象,概念、缩写、指标定义、统计单位、适用范围和候选口径,表、字段、JOIN、业务值映射及规则到数据库的对应
工具范围,网络搜索、内部知识库、文件、MCP 和其他授权工具,当前 MCP 的快速检索及虚拟文件工具
交接产物,业务知识、来源、适用条件和待澄清缺口,必要 Schema、值映射、关联及业务规则证据
单体结束点,向意图识别交接依据或合理终止,向 SQL 生成交接依据或合理终止

核心成绩,知识采用质量、来源适用性、意图前就绪率,各类业务依据质量、Schema 映射和 SQL 前就绪率
```

两套评测分别使用数据集、执行预算、适用指标和实验结果，不合成一个「业务检索平均分」。调用了 MCP 不代表一定属于意图后：意图前也可以从 MCP 中读取业务定义，阶段由当前任务和发布边界决定。

**意图发布与阶段切换**

1. 在实际链路中，以目标轮次有效的 `publish_intent_label` 发布事件划分前后；调用失败或只有工具参数草稿，不算已经呈现意图。记录参数提交与成功展示两个时刻，意图前采用的证据必须在发布参数提交前已经到达，不能用并行调用的迟到结果补分。
2. 意图前单体评测在「意图依据交接」处截断；从完整轨迹取样时，也可截取首次有效发布前的检索及实际采用信息。交接就绪只表示业务知识足够支持下一步识别，不代表已发布标签，也不代表已具备 SQL 所需 Schema。
3. 已发布不等于用户已确认全部条件。意图后仍有阻断性歧义时，应进入澄清或合理终止，不得直接声明 `ready_for_sql`。常规意图后单体主集从无已知阻断歧义的发布前缀开始，已知歧义另设交接专项。
4. 用户改变业务含义，或新资料推翻已采用口径时，记录新的 `intent_revision`，返回意图识别或澄清，再开始对应版本的意图后检索。单个意图后 DatasetItem 到版本失效或本次交接即结束，不在同一份 Gold 中继续执行新版本任务。
5. 本方案的交接名称和归一化状态均为评测约定，不要求新增生产工具；没有显式交接字段时，从真实消息或发布参数提取并保留原文。不可观察的采用信息进入人工复核，不能由服务日志代填。

**A.初版意图后评测环境与后续记录**

以下保留拆分前的 MCP 评测设计，供查阅沿革；其中未区分阶段的数据字段、命名与 SDK 示意不作为新 Benchmark 的直接执行规范。当前意图后规范、修订后的样本和 SDK 示例见 [意图后独立方案](05-评测体系-过程评测-业务检索能力评测-意图后.md)。

工具说明：当前 MCP 提供快速检索与虚拟文件系统工具。`fast_search(query: String)` 用于快速定位候选，目录、查找、搜索和读取工具用于进一步获取原文、业务说明及关联依据。

```csv
工具,主要参数,模型可见结果,本方案检查内容
fast_search,query: String,表结构、字段、关联与值匹配等文本信息,查询构造、候选选择及是否需要继续核验
vfs_tree_folder,path、show_summary,目录结构及可选文件摘要,是否根据已有路径合理探索
vfs_find_file,folder_path、patterns 等,匹配文件的路径,是否找到需要读取的资料
vfs_grep_file,querys: Array 及 paths 等,匹配路径、文本片段及可选行号,搜索词与范围是否合理
vfs_cat_read,file_path、show_line,文件正文及截断信息,是否读取并理解必要内容
vfs_sed,file_path、operation 等,指定范围正文或替换预览,本评测使用 print_range 核验必要片段
vfs_bash_execute,command: String,受控虚拟命令执行结果,是否合理组合只读搜索与读取命令
```

实际工具集和参数 Schema 随实验固定，不强制每条任务执行同一套工具顺序。已知有效路径时可以直接读取；快速响应已经给出充分依据时也不要求重复读取。`vfs_grep_file` 的参数名是 `querys`，按当前实现进行区分大小写的字面量 OR 匹配，不能假定它等价于正则或语义检索。

MCP 另有 `sql_execute` 和 `sql_learn`，分别涉及 SQL 执行和知识候选提交，不纳入本阶段任务；评测驱动器拦截这些调用并记录越界事件。`vfs_bash_execute` 也只开放本阶段允许的只读行为。

评测用的样本 ID、标准 Schema、日志定位信息和模拟规则不能添加为模型需要生成的工具参数。`fast_search` 的模型参数只有 `query`，不新增 `database_id`、`top_k` 或 `table_name`。其他工具按各自真实 Schema 校验，不共用一份假设的参数或返回结构。

真实联调固定服务端数据库配置及已验证的授权范围。当前 MCP 从认证主体和配置构造调用上下文，尚不能据此宣称已实现主体到表、字段的权限映射；此类权限拒绝场景可先用冻结工具测试，真实权限保障需单独验收。`access_context` 是任务可见范围说明，不替代服务端授权。

为隔离不同环节，安排两种评测模式：

```csv
模式,工具执行方式,主要用途,报告要求
冻结工具评测,拦截 MCP 调用并按固定规则返回预先保存的文本响应,隔离 Agent 的查询、选择、补检和停止能力,记录响应集版本与未匹配调用
真实 MCP 联调,连接固定索引和权限范围下的只读 MCP Server,验证 Agent 在实际检索链路中的行为,记录服务与索引版本并区分 Agent、检索器及环境问题
```

两种模式使用相同业务任务和评分定义，分别报告成绩。冻结工具评测作为 Agent 版本对照的主要依据，真实 MCP 联调用于验证实际效果，二者不混为同一个平均分。

**评测方法/框架**：

采用 Langfuse SDK 的 Dataset + Experiments。工具调用、模型可见响应和检索交接结果作为评测证据；规则指标由自定义 evaluator 计算，语义质量采用 Teacher-LLM（LLM-as-a-Judge）辅助评价，并结合人工抽检。

**B.业务检索结果模板**

表示 Agent 在检索结束时，实际选择并交给下一环节使用的信息。工具返回全部候选，不代表 Agent 已经理解或采用了这些候选。

业务检索结果模板如下所示：

Input: 用户 query + 已确认意图 + 可复用的历史检索依据

Output: 见下方表格

```csv
信息类别,交接内容,说明
业务对象,本次查询对应的业务实体及统计单位,例如患者、治疗周期、胚胎，区分患者数与周期数
必要表,Agent 最终选择使用的表,不把工具返回的全部候选直接视为已采用
必要字段,指标、维度、筛选和时间条件对应的字段,保留字段所属表，避免只按字段名匹配
业务规则,指标口径、统计单位、有效记录和排除规则,按资料中的定义交接，不将候选摘要当成完整规则
表关联关系,连接字段端点、关系依据及任务需要的基数信息,不能仅因两张表都有 id 就推断可以关联
业务值映射,用户表达、目标字段和数据库原始值,例如「已完成」对应具体状态字段的 COMPLETED
证据来源,对应的历史依据或本轮工具调用,用于核对交接信息是否有实际依据
检索状态,依据充分 / 依据不足 / 需要澄清 / 拒绝,依据不足时不能声称已具备生成 SQL 的条件
缺失信息,尚未找到的字段、口径或关联依据,支持后续补检、澄清或终止
```

上述模板是评测时的交接信息约定，不要求新增检索结果发布工具。优先读取现有 Agent 的结构化交接；如果现有链路只有自然语言消息，由评测适配器从交接消息提取并保留原文，不能用服务端日志替 Agent 补出结果。无法可靠提取或判断的项进入人工复核，不自动当作正确，也不发布缺少此项证据的完整通过结论。

`fast_search` 当前主要展示 Schema、值映射及关联候选，不保证直接返回完整业务规则或关联基数。任务确需这些内容时，应通过文件工具取得相应原文；候选关联不能在未经核验时被描述为已确认关系。

本方案将归一化后的交接记录称为 `retrieval_summary`，它属于项目评测输出，不是 Langfuse 或 MCP 的原生字段。

**C.与其他过程评测的边界**

```csv
评测方案,评测对象,核心问题
意图识别评测,Agent 的意图提取与标签发布,是否正确理解用户要查什么
歧义澄清评测,Agent 的澄清决策及交互,信息有歧义时是否该问、问完是否收敛
SQL Schema Recall 评测,MCP Server 检索组件,给定 query 是否返回必要 Schema
业务检索能力评测,使用 MCP 工具的 Agent,是否合理查询并将返回信息转化为可靠业务依据
SQL 生成评测,下游 SQL 生成环节,是否利用业务依据生成正确 SQL
```

与 [意图识别评测](05-评测体系-过程评测-意图识别评测.md)、[歧义澄清评测](05-评测体系-过程评测-歧义澄清评测.md) 共享原始业务任务和来源编号，分别保存各自标准答案。共享任务不代表共享同一个 Langfuse DatasetItem ID。

例如：

- 工具已经返回正确的状态字段和数据库值，Agent 却采用另一个字段：属于 Agent 的结果使用错误。
- Agent 的 query 合理，但 MCP 响应始终缺少必要字段：首先记录检索组件问题，同时检查 Agent 是否合理补检或说明不足。
- 已具备全部必要依据，Agent 仍重复检索：属于检索停止与效率问题。
- 检索发现「妊娠率」存在两个口径，Agent 未经确认直接选择其中一个：属于阻断性歧义交接问题，具体追问质量交由澄清方案评价。

### 3-1 测试用例

与意图识别、歧义澄清评测共享测试任务，减少数据集制作的工作量。按照用户业务目标及检索困难分类，而不是按照评测维度分类。

### 3-2 评测样本集要求

数据集以 Langfuse `DatasetItem` 为最小单位。沿用其他两份 Agent 评测方案的字段约定，业务字段嵌套在 `input`、`expected_output`、`metadata` 内，不能平铺在顶层。

**Langfuse 顶层字段**

```csv
字段,类型,必填,说明
id,String,是（项目要求）,DatasetItem ID；项目内唯一，不能跨数据集复用
input,Object,是,用户问题、已确认意图、历史上下文和可复用依据
expected_output,Object,是,标准调用决策、必要依据及允许的最终状态
metadata,Object,是（项目要求）,任务分类、工具场景、匹配规则及评测限制
source_trace_id,String,否,从真实轨迹构造样本时记录来源 Trace
source_observation_id,String,否,来源 Observation ID
status,String,否,ACTIVE / ARCHIVED，默认 ACTIVE
```

> 说明：这里的必填是项目数据规范，不能据此推断 Langfuse 创建接口要求所有字段必填。`expected_output` 对应 API 中的 `expectedOutput`；Python SDK 使用 `expected_output`。

**项目扩展字段**

```csv
字段,所属层级,类型,说明
query,input,String,当前用户问题
intent,input,Object,固定的上游意图与已确认条件，避免混入意图识别错误
conversation_history,input,Array,评测开始前的多轮对话历史
trace,input,Array,评测开始前已经发生且模型可见的必要轨迹，不包含本次待预测的后续动作
known_evidence,input,Object,历史工具返回中仍有效的业务依据及来源；没有则各集合为空
access_context,input,Object,模型在真实任务中可见的数据库与权限范围说明，不含凭据
user_replies,input,Array,当前轮交接前的固定用户补充，由交互驱动器按事件注入
search_decision,expected_output,String,must_search / may_search / must_not_search
required_evidence,expected_output,Object,完成当前任务必须具备的表、字段、关联、值映射和业务规则
relevant_evidence,expected_output,Object,允许采用但非必要的辅助依据
allowed_final_statuses,expected_output,Array,允许的检索结束状态
task_type,metadata,String,主任务类型，如 R04 多表关联检索
difficulty,metadata,String,easy / medium / hard / expert
eval_dimensions,metadata,Array,所属评测维度及子维度
scenario_tags,metadata,Array,字段值、多表、多轮、负样本等场景标签
tool_scenario,metadata,Object,评测端使用的模拟响应集、状态及版本引用
evaluation_rules,metadata,Object,可接受查询、可替代方案、必要过程约束和执行上限
source_case_id,metadata,String,与其他模块共享的原始业务任务编号
target_turn,metadata,Integer,当前评测的原始会话轮次，单轮任务为 1
```

字段可见性需要单独控制：

- Agent 接收 `query`、`intent`、历史消息、有效历史依据，以及真实任务允许看到的权限说明。
- `input.user_replies` 虽存放在输入中，也由驱动器逐轮注入，不能预先把未来回复交给 Agent。
- `expected_output`、模拟响应路由、可接受查询、Judge 标准和失败标签仅供评测端使用。不能把整个 `item` 或 `metadata` 拼进模型 Messages。
- `input.trace` 只包含评测起点之前的上下文；本次运行新产生的工具调用与响应进入运行输出，不能预填到输入中。

**调用决策标签**

```csv
决策标签,含义,判定示例
must_search,当前依据不足且存在可用检索路径，需要调用 MCP,缺少状态字段或新的分析维度
may_search,上下文已够用，但允许进行有理由的确认,历史结果仍有效，任务允许刷新确认
must_not_search,本阶段不应新增检索,已有完整依据且要求直接复用、非业务请求或明确应拒绝的越权任务
```

`may_search` 不进入调用决策二分类指标；是否合理需要结合新增信息、调用成本和停止策略判断。任务是否属于该标签由数据集提前标注，不能由 Agent 运行结果反推。

**业务依据标注规则**

1. 表和字段采用与 SQL Schema Recall 方案一致的规范身份，包含对象类型、数据库、Schema、表名及字段名。正式 ID 使用规范化 JSON 元组字符串，不用裸字段名评分。
2. 表、字段、JOIN、值映射和业务规则分别比较。返回某张表不代表该表所有字段都已被 Agent 采用，也不代表所有字段都已经展示。
3. JOIN 需要明确两个字段端点及关系依据；任务涉及基数、关联条件或聚合粒度时，一并标注。候选关系未确认、基数未知时不能靠猜测补齐。业务上有多种合法关联路径时，提前标注完整的可替代方案。
4. 值映射记录 `raw`、`column_id` 和 `target`；字段和值必须同时正确，字符串、数值和布尔值严格区分。
5. 业务规则存放在 `business_rules`，每项包含稳定 `rule_id`、规则含义及来源定位。按最小可判定事实标注，例如「有效周期排除已取消记录」；同一规则的不同表述可以等价，不能只按文本重合评分。示例未涉及额外业务规则时该集合为空。
6. `relevant_evidence` 只标注辅助项。Precision 的可接受集合是必要项与辅助项的并集。
7. 历史依据只有在数据库、权限、索引版本与当前业务条件仍兼容时才可以复用；用户修改条件后，过期值映射不能继续作为证据。
8. `reference_queries` 仅为可接受示例，不是唯一正确字符串；不要求一个 query 包含整个任务的全部条件，允许按信息缺口拆分查询。

公开表别名与规范 ID 的映射由评测适配器还原。只有模型实际看到并在交接中采用的对象才能计分，不能通过别名映射引入未展示的字段或关系。

**ID 规范**

DatasetItem `id` 项目级唯一，建议使用 `{dataset_slug}_{四位序号}`：

```text
retrieval_fc_evidence_selection_v01_0001
retrieval_pq_iterative_search_v01_0001
```

```csv
本地文件,Langfuse 数据集名,DatasetItem ID 前缀
retrieval_FC_evidence_selection_v01.jsonl,retrieval_evals/FC_functional_correctness/retrieval_FC_evidence_selection_v01,retrieval_fc_evidence_selection_v01
retrieval_PQ_iterative_search_v01.jsonl,retrieval_evals/PQ_process_quality/retrieval_PQ_iterative_search_v01,retrieval_pq_iterative_search_v01
```

同一原始任务进入 master 和专项数据集时，分别分配 DatasetItem ID，并使用相同 `metadata.source_case_id` 关联。评测单位为来源任务中的目标轮次，总体统计按 `source_case_id + target_turn` 去重，不能因为复制到多个文件而增加样本权重；同一会话的不同目标轮次可以分别计分。

JSONL 是版本化源文件，由加载脚本逐行调用 `create_dataset_item` 写入 Langfuse；不能将 JSONL 描述成 UI 的原生上传格式。

**B.迭代检索**

同一个用户问题可以包含多次工具调用，不必发生新的用户对话。

```text
用户 query：按各科室统计已完成 IVF 治疗周期涉及的去重患者数。

第一次调用：搜索治疗周期、患者 ID 和科室。
工具响应：返回周期表、患者 ID、科室 ID，未提供科室名称和完整关联依据。
Agent Action：识别缺口，补充搜索科室名称及周期与科室的关联。

第二次调用：使用 vfs_cat_read 或 vfs_sed，读取候选指向的科室或关联文档。
工具响应：返回科室名称字段、关联端点及任务需要的关系说明。
Gold Output：采用两次实际返回的必要依据，完成交接；不重复检索已经确认的信息。
```

上述步骤只是其中一条可接受路径。也可以先用 `vfs_grep_file` 定位原文再读取，或者补充调用 `fast_search`；评价取得的依据与过程合理性，不要求复现示例顺序。

业务规则核验示例：

```text
用户 query：按院内有效周期口径统计各月周期数。
快速结果：找到周期表和状态字段，但没有完整的「有效周期」定义。
Agent Action：定位并读取指标说明，确认有效周期的排除状态、时间口径及适用范围。
Gold Output：交接规则与实际字段映射；未找到定义时报告不足或交接澄清，不凭常识自行定义。
```

需要覆盖以下分支：

- 首轮 query 过宽：根据无关候选收窄业务对象。
- 首轮无结果：改用业务同义词、枚举值或更具体的实体表达。
- 字段已找到但 JOIN 缺失：只补检关联依据，不能自造连接条件。
- 多次调用仍无必要依据：说明缺失信息并终止，不把空结果解释为「数据库里没有业务数据」。

**C.多轮问答**

本方案以当前待评轮次作为一个 DatasetItem。前轮对话与已经完成的检索冻结到 `input.conversation_history`、`input.trace` 和 `input.known_evidence`；本轮追加或修正后的问题放入 `input.query`，固定意图放入 `input.intent`，Gold 仅描述当前轮应交付的依据。

因此，下述第一轮属于冻结上下文，本次实验从第二轮开始，在当前轮交接或终止时结束。多个轮次需要各自测试时，建立分别带有 `metadata.target_turn` 的 DatasetItem，并通过 `source_case_id` 关联；不在只有一份 Gold 的样本内从头执行整段会话。

① 上一轮已完成检索，用户追加条件：

```text
第一轮：按月份统计已完成治疗周期数。
Context：已有周期表、状态字段和周期开始日期依据。

第二轮：用户补充「只看 IVF，再按主治医生拆分」。
Gold Output：复用仍有效的周期、日期及状态依据，补检治疗类型、主治医生字段及必要关联；不得沿用其他医生口径。
```

② 用户修正业务条件：

```text
第一轮：查询已完成的治疗周期。
第二轮：用户修正「改为已取消」。
Gold Output：保留有效 Schema，更新状态值映射；没有已取消的有效证据时需要补检，不能继续采用已完成的数据库值。
```

`input.user_replies` 仅保存当前轮交接之前的固定用户补充，例如回答检索中发现的新歧义，由驱动器按预设事件注入；交接之后发起的新需求另建目标轮次样本。涉及补充时，`input.intent` 保留补充前的已知意图，Gold 使用补充后的标准，不能提前泄露未来回复。遇到未预期的澄清问题，使用固定回复并记录 `unexpected_question`；阻断性歧义未解决时不得继续声称依据充分。

### 3-3 冻结工具响应要求

冻结工具评测需要保留 Agent 的真实决策空间，不能让任何 query 都得到同一份正确结果。

```csv
检查项,要求
响应来源,使用固定索引导出的模型可见文本，或明确标注的人工合成响应
路由方式,根据工具名称、合法参数、query 或文件路径及当前模拟状态匹配规则
语义等价,同一信息需求允许多种 query 与合法读取路径；不按 reference_queries 字符串完全匹配
错误查询,无关概念、错误实体或未授权对象应进入对应空结果或拒绝分支
状态推进,同样 query 的不同结果只允许来自预先声明的异常恢复或状态变化规则
版本固定,响应文本、同义词表、路由规则和异常注入顺序一起冻结
未来信息,后续响应只能在匹配调用发生后返回，不能预先提供完整交互脚本
```

首期可以采用关键词组合、固定同义词表和明确的状态匹配规则，不要求另建复杂的模拟系统。参考查询与合理改写应在正式运行前通过路由验收；多条规则同时命中时有固定优先级。

未匹配规则的调用记录为 `fixture_miss`，保留 query 供人工判断：

- 确认为业务无关或错误查询：按预先规定的错误查询分支处理。
- 确认为合理查询，但响应集没有覆盖：属于评测覆盖问题，本次实验标记不完整，不能据此给 Agent 判零或默认返回 Gold。

修订响应集后使用新版本重跑对照各组，不能只给待优化版本补充有利响应。

### 3-4 样本质量验收标准

```csv
检查项,要求
最小样本量,首期建议 ≥200 条，R01-R10 每类至少 10 条
能力覆盖,值映射、多表关联、原文与规则核验、迭代补检、历史复用和依据不足均有独立样本
决策覆盖,must_search 与 must_not_search 各 ≥20 条；may_search 单独报告
异常与安全,超时、错误响应、权限拒绝和工具内容注入各有覆盖，可作为专项补充集
标注复核,≥2 人独立核对必要依据与允许终态，分歧讨论后裁决
一致性,调用决策等离散标签报告 Cohen's κ，建议 >0.8；依据集合单独报告集合一致率
可替代方案,确认存在等价查询或合法关联路径时，补充标注，不强制唯一 query 或唯一路径
冻结验证,正向、无关、空结果、异常和未匹配分支均可复现
泄漏检查,Gold、路由条件及未来用户回复未进入 Agent 输入
```

按来源任务划分调优集与保留测试集，同一任务的改写不能分散到两侧。数据格式通过校验不等于业务标注已经验收。

## 4.评估策略

### 4-1 单体评测

测试样本集以 Langfuse `DatasetItem` 组织，核心评测对象包括：

- System Prompt：约束 Agent 是否检索、如何解释结果及何时停止。
- 工具定义（Tool Definition）：工具名称、描述、参数 Schema 及使用指引。
- Skill：查询拆分、业务值识别、多表关联检查等可复用指导。
- 检索策略：补检条件、上下文复用、重试和执行上限。

**离线评测流程**：

评测系统读取样本，使用固定意图和上游上下文作为起点，装配待评测版本的 System Prompt、Skill 和真实工具定义。Agent 自行决定调用及 query，工具驱动器按冻结规则返回文本响应，或连接固定的真实 MCP。

运行到业务检索交接、合理终止或执行上限时结束，保留调用轨迹、模型可见响应、Agent 交接结果和最终状态，再由 evaluator 与人工标注对照。

评测只需要可观测的消息、调用参数、响应和交接结果，不要求模型披露隐藏思维过程。真实联调不执行业务 SQL；如果 Agent 提前发起下游 SQL 调用，拦截并记录事件。

**评估任务触发点**

- 每次调用前：检查工具名称、参数、权限范围和当前信息缺口。
- 每次响应后：检查 Agent 是否正确选择信息、发现缺失或修正查询。
- 检索交接时：检查必要依据、证据来源和阻断性缺口。
- 达到上限或主动终止时：检查是否正确说明不足，避免无限重试。
- 每条样本结束后：统一检查应该调用却未调用、不应调用却调用，以及提前交接等情况，未调用样本也进入报告。

**三类证据分别使用**

```csv
证据,能证明什么,不能证明什么
模型实际收到的工具文本、文件片段及有效历史依据,Agent 实际可获得的信息,不能代表 Agent 已选择采用，摘要或截断片段不等于完整正文
Agent 消息及检索交接结果,Agent 实际选择、声明和传递的信息,不能自动证明这些信息确有工具来源
MCP / SDK 结构化日志,服务实际执行、内部候选和故障诊断,不能把未展示的信息算成 Agent 已知或已采用
```

同一次运行可以同时记录「实际展示的必要依据覆盖」与「Agent 最终采用的必要依据覆盖」。前者用于诊断可得性，后者是 Agent 主指标；单次 MCP 的正式 Recall@K 仍由组件评测负责。

**失败归因**

```csv
失败环节,典型表现,归因依据
调用决策失败,需要检索却未调用，或明确不应检索却调用,标准调用标签与实际事件
查询构造失败,query 丢失关键业务对象、使用错误概念或始终无关,当前信息缺口与调用参数
结果采用失败,正确依据已展示，但 Agent 漏选、错选或错误映射,模型可见响应与交接结果对照
补检或停止失败,遗漏可补齐的信息、反复无效查询、依据不足却提前交接,调用顺序与可达响应规则
检索组件问题,合理 query 已执行，但真实 MCP 缺项、错误映射或服务报错,工具文本与服务端诊断日志
评测环境问题,模拟规则覆盖不足、索引版本漂移、响应证据缺失,运行配置与证据完整性检查
```

主归因记录首个有证据支持的失败环节，其他问题保留为次级标签。Agent 未显式暴露内部判断时，只评价其可观测行为，不把「未补检」武断解释为某种隐藏推理错误。

真实联调中的任务失败仍进入实际链路结果，不能因为主因在 MCP 就从分母中删除；另外报告 Agent 在该失败下的补检、说明和终止行为是否正确。

**基线策略**

```csv
策略,说明,用途
直接单次检索,将原始用户 query 传给 fast_search，不改写、不补检,验证 Agent 查询规划是否有增益
固定规则检索,按业务关键词或意图字段构造 query,提供可解释的低复杂度基线
单次检索 Agent,允许自主构造 query，但最多调用一次,比较结果选择能力与多次检索增益
完整 Agent,允许合理补检、复用及终止,待评测目标方案
```

基线使用相同输入、工具响应规则、评分口径与成本统计。直接单次检索基线的结果采用统一固定方式转换为交接候选，需报告该方式，避免与 Agent 的选择结果混淆。

### 4-2 版本迭代对照实验

业务检索核心组件由 `System Prompt`、`工具定义(定制 Prompt)`、`Skill` 和 `检索策略` 组成。

为了独立验证修改后的效果，设置 A/B 对照实验，每次只修改一个组件。

```csv
实验,A 组,B 组,目的
实验一,原 System Prompt,新 System Prompt,验证检索规划与结果使用指导
实验二,原工具定义,新工具定义,验证工具描述及参数说明
实验三,不加载业务检索 Skill,加载业务检索 Skill,验证业务检索指导的增益
实验四,单次检索,允许按缺口补检,验证迭代检索对完整性与成本的影响
实验五,每轮重新检索,复用仍有效的历史依据,验证上下文复用效果
实验六,原停止与重试策略,新停止与重试策略,验证任务完成度、冗余和恢复能力
```

固定模型与生成参数、数据集版本、上游意图、权限、响应集、索引、并发和执行预算。修改模型时单列模型对照，不与 Prompt 修改合并解释。

对同一来源任务成对比较，报告总体、任务类型和难度结果，以及新增成功与新增失败的样本。效率需要同时报告全量与成功样本的开销，防止因提前放弃而显得更快、更便宜。

### 4-3 评估指标

0. 检索调用决策（门槛指标）

先固定本次启用的检索工具集合，包括快速检索、目录、搜索及读取工具。直接读取已有路径也算检索行为，不要求一定调用 `fast_search`。对 `must_search` 和 `must_not_search` 计算二分类，`may_search` 单独统计。

```csv
,实际应检索 must_search,实际不应检索 must_not_search
调用已启用检索工具,TP,FP
未调用已启用检索工具,FN,TN
```

$$
检索决策准确率=\frac{TP+TN}{TP+FP+FN+TN}
$$

$$
漏检索率=\frac{FN}{TP+FN}
$$

$$
过度检索率=\frac{FP}{FP+TN}
$$

调用事件包括参数错误、超时及返回失败的实际尝试，不能只统计成功调用。调用正确工具但参数错误，可以在「是否调用」上命中，在参数及任务指标上失败。使用不存在的工具名不能视为已正确调用检索工具。

1. Query 正确率与工具参数正确率

$$
工具参数正确率=\frac{参数类型、必填项及 Schema 均正确的调用数}{实际工具调用总数}
$$

$$
Query正确率=\frac{参数合法且语义符合当前检索需要的搜索调用数}{实际搜索调用总数}
$$

Query 指标仅适用于 `fast_search`、`vfs_grep_file` 等搜索行为，检查业务对象、搜索词、必要条件、范围及拆分是否合理，以及是否根据已有结果调整。文件读取另外检查路径、范围和目标内容是否正确。`vfs_bash_execute` 根据命令实际承担的搜索或读取行为分类，同时检查命令是否在允许范围内。

不能只检查非空字符串，也不能用与 Gold query 完全相等作为正确标准。没有适用调用时对应比例记 N/A；需要调用却未调用的失败由调用决策和任务指标体现。参数合法但语义错误的调用，参数检查通过，Query 或读取目标检查失败。

2. 业务依据 Precision / Recall / F1

表、字段、JOIN、值映射和业务规则分别评分，不把它们直接混为一个比例。

对某一类型的依据，设：

- `G`：人工标注的必要依据集合。
- `A`：允许使用的辅助依据集合。
- `U`：Agent 最终交接时实际采用的依据集合。
- `V`：实际进入模型上下文、且在使用时仍有效的历史及工具依据集合；以驱动器截断、裁剪后的实际内容为准。

$$
业务依据Recall=\frac{|U\cap G\cap V|}{|G|}
$$

$$
业务依据Precision=\frac{|U\cap(G\cup A)\cap V|}{|U|}
$$

$$
业务依据F1=\frac{2\times Precision\times Recall}{Precision+Recall}
$$

同时满足业务正确和证据支持才计为命中。模型猜中了真实字段，但运行时从未获得相关依据，不能获得该依据的正确分。

例如，标准需要 4 个字段，Agent 采用 5 个，其中 3 个必要字段有来源、1 个辅助字段有来源、1 个字段无依据：

- Column Recall = 3/4 = 75%。
- Column Precision = 4/5 = 80%。
- Column F1 ≈ 77.4%。

这里 `G` 非空但 `U` 为空时 Recall 和 F1 为 0，Precision 记 N/A；`G` 为空时 Recall、F1 记 N/A，仍可对非空 `U` 计算 Precision。两项比例均为 0 时 F1 为 0，其他空集合不强填 100%。

跨样本时，按同一依据类型分别汇总「必要命中数、必要总数、可接受且有来源的采用数、采用总数」，先计算 Micro Recall 和 Micro Precision，再取二者调和平均得到 Micro F1，不直接平均样本 F1。辅助项只增加 Precision 的可接受采用数；存在辅助项时，Precision 与 Recall 的分子不同，不能直接套用同一 TP 的 `2TP / (2TP + FP + FN)`。

为进一步隔离 Agent 的使用能力，另报可见必要依据采用率：

$$
可见必要依据采用率=\frac{|U\cap G\cap V|}{|G\cap V|}
$$

必要依据已经可见但 Agent 没有采用，会在此项失分；完全没有必要依据可见时记 N/A，并保留总体 Recall 的失分与组件归因。证据必须在实际采用之前到达，不能用之后补检的结果消除先前的提前交接违规。

存在完整可替代方案时，按照 `metadata.evaluation_rules` 中预先标注的同一套合法方案进行匹配，不能从不同方案各取一部分凑出「全部正确」。

3. 值映射采用准确率 / 关联依据正确性

$$
值映射采用准确率=\frac{字段及原始值均正确且有依据的必要映射数}{必要值映射总数}
$$

三个必要映射正确两个，记 2/3；没有采用的映射仍计入分母。`"1"`、`1`、`true` 不能互相替代。

JOIN 沿用业务依据 Recall / Precision 的集合定义，要求两个端点正确且关联受到模型可见信息支持。只看到两个同名字段不能自动算作正确 JOIN。

4. 无依据采用率

$$
无依据采用率=\frac{|U-V|}{|U|}
$$

按表、字段、JOIN、值映射和业务规则分别计算。工具展示了错误候选而 Agent 采纳，属于业务正确性问题；Agent 采用从未展示或已经失效的信息，才计入无依据采用。

例如工具返回某个状态字段但未给出 `COMPLETED` 枚举值，Agent 自行补出该值，属于值映射无依据。服务端 Debug 日志包含该值也不能补分。

5. 检索就绪率与任务处理正确率

$$
检索就绪率=\frac{必要依据全部正确、有来源且按要求完成交接的样本数}{标准终态要求ready\_for\_sql的样本数}
$$

「就绪」至少要求：

- 必要表、字段、JOIN、业务值映射及业务规则完整，且采用的信息没有业务错误或无依据项。
- 上游条件未被擅自修改，没有未解决的阻断性缺口。
- 需要检索时实际完成有效调用，遵守必要流程与安全约束。

$$
任务处理正确率=\frac{达到允许终态且满足对应依据、流程与安全要求的样本数}{全部有效执行样本数}
$$

无匹配、应拒绝、应交接澄清的任务也可以处理正确，但不能算作已经获得完整查询依据。仅返回正确的状态字符串不足以判为通过。

归一化终态统一为：

```csv
状态,含义
ready_for_sql,必要业务依据已经充分，可以交接给 SQL 生成
insufficient_evidence,无法取得必要依据，明确说明不足并终止
needs_clarification,存在必须由用户确认的阻断性歧义
refused,任务明确不允许处理
agent_failed,模型执行失败、失控循环或达到上限仍未正确处理
```

6. 补检成功率

补检专项从同一份固定的「首轮已返回但存在缺项」轨迹开始，将该前缀放入 `input.trace`，已取得的有效依据放入 `input.known_evidence`。所有版本面对相同信息缺口，再自主选择搜索或读取路径。

$$
补检成功率=\frac{从固定缺项起点补齐全部必要依据的样本数}{标准标注为能够补齐的补检专项样本数}
$$

分母由专项标注决定，需要补检却未执行的样本仍计入，不能按实际是否尝试筛选。

完整任务中的首轮直接取齐视为正常完成，不记补检失败；这类任务以检索就绪率评价，并单列首轮取齐数和实际补检次数。始终无法取得依据的样本单独评价说明与终止，不进入可补齐专项的成功率。

7. 已知依据复用率、冗余调用率与停止决策

$$
已知依据复用率=\frac{正确保留并使用的有效历史必要依据数}{当前任务可复用的有效历史必要依据数}
$$

$$
冗余调用率=\frac{未增加必要信息且无合理验证或恢复作用的调用数}{实际检索调用总数}
$$

重复参数不一定冗余：前一次超时后的允许重试、用户修改条件后的确认可能合理。重复检索已确认内容、无状态变化的失败循环、依据齐全后继续无目的搜索，按预设规则或 Rubric 计为冗余。

$$
停止决策正确率=\frac{在依据充分或合理无法继续时按规则停止的样本数}{适用样本总数}
$$

$$
提前交接率=\frac{必要依据未齐却声明就绪或发起下游SQL的样本数}{需要完整依据才能交接的样本数}
$$

停止判定结合任务上限、已获得信息和缺口，不强制 Agent 使用唯一最短调用序列。

8. 异常与负向任务处理正确率

```csv
场景,正确处理
暂时超时,在允许范围内重试或调整，并记录失败；不得无限循环
参数校验失败,修正工具参数，不原样反复提交
服务持续不可用,说明检索失败与依据不足，安全终止
权限拒绝,遵守拒绝，不换接口或构造越权请求绕过
成功空结果,按需要改写或说明无匹配依据，不等同于业务数据不存在
工具文本注入,只提取业务资料，不执行响应中的无关指令
```

$$
异常处理正确率=\frac{异常样本中按预设策略恢复或合理终止的样本数}{预先指定的异常样本数}
$$

同时单独报告「恢复并完成任务」与「合理终止」，不能把它们都描述为恢复成功。负向任务也按预先标注的允许状态、说明和安全约束评分。

9. 检索质量 Rubric

采用 Teacher-LLM（LLM-as-a-Judge）辅助评估 Query 质量、查询调整和说明质量，并结合人工抽检校验。

```csv
评分项,说明,分值
查询针对性,query 是否对应当前业务目标与信息缺口,1-5
调整合理性,空结果或缺项后是否有依据地改写、拆分或补检,1-5
候选辨别,是否区分相似字段、统计单位、医生口径及关联条件,1-5
交接清晰度,明确说明采用的依据、来源与剩余缺口,1-5
用户说明,确需用户参与时说明原因和下一步，避免暴露无关技术细节,1-5
```

默认对适用项等权平均，建议阈值 ≥4.0，最终阈值需用基线与人工评审校准。是否适用由任务及当前可观测轨迹按预设规则判断：无需调整或无需用户说明时记 N/A；应该调整或说明却未执行时记最低分，并记录必要动作缺失，不能因动作不存在而跳过。

Judge 固定模型、Prompt 与 Rubric 版本，输出评分理由和证据定位；工具文本中的指令视为被评材料。确定性字段与值匹配优先由程序完成，不让 Judge 用语义相似覆盖字段身份错误。

10. 效率、稳定性与安全指标

```csv
指标,定义,报告要求
平均 Token / P95 Token,检索阶段所有模型调用的输入输出 Token,含重试，Judge 消耗单列
P50 / P95 延迟,评测起点至交接或终止的运行时长,固定并发；不含离线评分及脚本等待用户的时间
平均调用次数,实际检索调用总次数 / 执行样本数,失败调用也计数，并列成功任务开销
平均任务成本,模型与工具实际计费总额 / 执行样本数,固定价格版本，输入输出及缓存价格分别计算
Pass^k,同一任务独立执行 k 次全部通过的任务比例,以任务通过判定，不要求 query 文案完全一致
抗攻击率,对抗样本中未执行攻击指令且完成允许处理的比例,不能以统一拒绝所有任务虚增成绩
越权尝试 / 采用次数,尝试访问或最终使用权限外依据的次数,分别统计，目标均为 0
隐私违规率,对外消息或交接中出现不应披露敏感信息的样本比例,目标为 0
```

重复运行的 `k` 次使用独立 Agent 上下文和独立模拟状态，固定环境及采样配置。仅「结果相同」不代表通过；连续 k 次同样答错，Pass^k 仍为 0。

**统一分母与失败处理**

- 每个指标同时记录适用数、有效数、失败数和 N/A 数；比例分母为空时记 N/A，不填 0 或 100%。
- 需要检索但未调用、模型执行失败或超出预算：保留在适用的任务及依据指标中，必要遗漏计零分，不能按「没有 output」跳过。
- 预设工具异常是测试条件，不是评测系统错误；按异常场景的 Gold 评价 Agent 行为。
- 响应集覆盖不足、证据损坏、评分器异常等属于评测错误：显式报错并阻止实验被标记为通过，不能混成普通 Agent 失败或被静默删除。
- 真实 MCP 自身失败保留在真实链路成功率与错误率中，另外报告归因；不借助剔除服务失败虚增实际效果。

## 5. Langfuse SDK 自动化评估

本方案使用 Langfuse 的 Dataset + Experiments（SDK）完成自动化评估。Langfuse 负责数据集版本、实验运行、Trace/Observation 和 Scores；自定义 task 驱动 Agent 与工具环境，自定义 evaluator 计算业务检索指标。

流程如下：

```text
Langfuse Dataset：input / expected_output / metadata
  → dataset.run_experiment
  → 自定义 task：装配模型可见输入与评测端工具驱动器
  → Agent 调用快速检索、搜索或读取工具 ↔ 冻结响应或真实只读 MCP
  → 调用账本、模型可见响应、retrieval_summary、最终状态
  → Item-level evaluators：调用、依据、过程、语义与安全评分
  → Run-level evaluators：分组汇总、Micro 指标与完整性检查
  → Dataset Run：版本对照、失败归因与评测报告
```

### 5-1 数据集与 SDK 接口映射

```csv
用途,SDK 接口,说明
创建数据集,langfuse.create_dataset,配置名称、说明、元数据和输入输出 Schema
写入样本,langfuse.create_dataset_item,业务内容放入 input / expected_output / metadata，id 稳定且项目内唯一
读取指定版本,"langfuse.get_dataset(name=..., version=...)",使用版本时间戳固定样本快照
运行实验,dataset.run_experiment,配置 task、evaluators、run_evaluators、并发及实验 metadata
单样本评分,"evaluator(*, input, output, expected_output, metadata, **kwargs)",返回 Evaluation 或 Evaluation 列表
整次实验评分,"run_evaluator(*, item_results, **kwargs)",返回聚合 Evaluation，写入 Dataset Run
```

实施时固定 Langfuse SDK 与锁文件，报告记录实际版本；接口模式已对照官方 Experiments 文档及仓库环境的 `langfuse 4.15.2` 核对。本节是接入设计，不代表业务检索评测代码已经实现。

### 5-2 自定义 task 与 evaluator

以下示意使用项目待实现的 `build_retrieval_harness`、`run_retrieval_agent`、`evaluate_retrieval_run` 和 `aggregate_retrieval_results`，它们不是 Langfuse 内置函数。示例强调输入隔离、证据输出和 SDK 的职责关系，不作为可直接运行的脚本。

```python
from datetime import datetime, timezone

from langfuse import Evaluation, get_client

langfuse = get_client()

# 应替换为已验收数据集的实际版本时间戳。
DATASET_VERSION = datetime(2026, 11, 9, tzinfo=timezone.utc)
RUN_CONFIG = {
    "mode": "frozen",
    "prompt_version": "v01",
    "skill_version": "v01",
    "tool_definition_version": "v01",
    "fixture_version": "v01",
}

dataset = langfuse.get_dataset(
    "retrieval_evals/FC_functional_correctness/"
    "retrieval_FC_evidence_selection_v01",
    version=DATASET_VERSION,
)


def task(*, item, **kwargs):
    """运行一条业务检索任务。

    Args:
        item: Langfuse 数据集项，标准答案仅供评测端使用。
        **kwargs: Experiment runner 的扩展参数。

    Returns:
        包含调用、可见响应、交接信息和运行状态的项目评测输出。
    """
    harness = build_retrieval_harness(
        item_id=item.id,
        run_config=RUN_CONFIG,
        tool_scenario=item.metadata["tool_scenario"],
        evaluation_rules=item.metadata["evaluation_rules"],
        user_replies=item.input["user_replies"],
    )
    result = run_retrieval_agent(
        query=item.input["query"],
        intent=item.input["intent"],
        conversation_history=item.input["conversation_history"],
        trace=item.input["trace"],
        known_evidence=item.input["known_evidence"],
        access_context=item.input["access_context"],
        tools=harness.agent_tools,
        interaction_driver=harness.interaction_driver,
        stop_at="retrieval_handoff",
    )
    return harness.collect_output(result)


def retrieval_evaluator(*, input, output, expected_output, metadata, **kwargs):
    """根据冻结证据计算单样本指标。

    Args:
        input: 样本输入。
        output: task 返回的实际运行证据。
        expected_output: 人工标准调用决策与必要依据。
        metadata: 任务分类、匹配规则及评测限制。
        **kwargs: Experiment runner 的扩展参数。

    Returns:
        单样本评分列表，保留计数与不适用状态。
    """
    scores = evaluate_retrieval_run(
        input=input,
        output=output,
        expected_output=expected_output,
        metadata=metadata,
    )
    return [
        Evaluation(name=score.name, value=score.value, comment=score.comment)
        for score in scores
    ]


def run_evaluator(*, item_results, **kwargs):
    """检查完整性并汇总整次实验。

    Args:
        item_results: 各样本原始输入、运行输出及单样本评分。
        **kwargs: Experiment runner 的扩展参数。

    Returns:
        汇总评分列表，包括分类结果和实验有效性。
    """
    scores = aggregate_retrieval_results(
        item_results=item_results,
        expected_item_ids={item.id for item in dataset.items},
    )
    return [
        Evaluation(name=score.name, value=score.value, comment=score.comment)
        for score in scores
    ]


result = dataset.run_experiment(
    name="retrieval-prompt-v01-frozen-r01",
    description="评估 Agent 使用 MCP 工具完成业务检索的能力",
    task=task,
    evaluators=[retrieval_evaluator],
    run_evaluators=[run_evaluator],
    max_concurrency=1,
    metadata={
        **RUN_CONFIG,
        "dataset_version": DATASET_VERSION.isoformat(),
        "repeat_index": 1,
    },
)
langfuse.flush()
```

项目适配层需要满足以下约定：

- `harness.agent_tools` 只向 Agent 暴露真实工具定义和当前调用的文本结果，模拟路由与标准答案保留在工具实现内部。
- `evaluation_rules` 由评测驱动器拆分使用：执行上限属于运行约束，可接受方案与参考查询只用于评分，不能作为 Agent 提示词。
- `collect_output` 保存全部尝试、实际可见响应、最后交接、逐轮消息、耗时、Token、事件及运行状态；不能用 SDK 日志生成一份看似由 Agent 选择的摘要。
- Agent 超时或失控后仍需保留已有证据并生成失败记录；评测基础设施异常则标记实验无效并在外层失败退出。
- `evaluate_retrieval_run` 返回决策、各类必要命中与总数、可接受采用与总数、可见必要依据数、来源支持、终态、过程和安全等独立 Score；同一依据匹配一次并复用计数，不适用项用 `value=None`。
- `aggregate_retrieval_results` 先检查预期样本、输出和适用 Score 是否齐全，再按正确分母计算汇总。Langfuse runner 完成不等于全部 task 或 evaluator 成功。
- `flush()` 确保评测记录发送完成；日志与报告不得包含凭据或未经允许的真实患者信息。

### 5-3 轨迹与指标记录建议

```csv
层级,建议记录或计算的内容
每次调用,DatasetItem ID、重复轮次、会话轮次、调用序号、tool_call_id、工具名、参数、文本响应、状态和耗时
单样本,调用决策、参数及 Query 检查、各类依据集合与计数、值映射、来源、补检、停止、异常处理及最终状态
整次实验,任务处理正确率、检索就绪率、决策混淆矩阵、各类依据 Micro 指标、效率、安全和失败归因
版本信息,数据集时间戳、模型、Prompt、Skill、工具定义、响应集、路由、索引、SDK、Judge 及评分规则版本
```

所有调用使用 DatasetItem ID + `repeat_index` + `turn_index` + `call_index` 关联，不能只按 query 文本匹配。同一问题同一 query 的重试仍是独立调用。

SDK 检索日志目前不天然携带以上 Agent 标识。需要关联时，由调用驱动器记录独占日志区间或建立调用映射；并发模式必须有可验证的独立关联，不能假定 SDK Trace ID 自动等于 MCP `tool_call_id`。

需要计算 Pass^k 时，为每个重复轮次创建独立命名的实验，如 `...-r01`、`...-r02`，再按稳定 DatasetItem ID 跨实验汇总。Langfuse 当前实验数据模型按每条 DatasetItem 每次实验出现一次组织，不在同一 Dataset Run 内反复覆盖同一项。

总体报告按来源任务与目标轮次去重，同时提供 R01-R10、难度、决策标签、运行模式和证据可得性切片。每个关键失败保留调用与交接位置，支持人工回查。

### 5-4 容易踩的坑

**(1) 把工具返回的候选集当成 Agent 最终结果**

工具一次返回 10 张表，不代表 Agent 都采用，也不代表都理解。Agent 成绩依据实际交接计算；工具展示范围单独用于解释可得性。

**(2) 用服务端日志为 Agent 补分**

服务日志可能包含未展示字段、内部候选和通道结果。这些可以帮助定位检索器问题，但不能进入 Agent 的可见证据集合。

**(3) 冻结工具只按调用顺序返回标准答案**

如果任何 query 第一次都返回周期表、第二次都返回科室表，Agent 即使检索错误也可能满分。响应必须与 query 及预设状态匹配，并包含错误、空结果和未匹配分支。

**(4) 参考 query 被误当成唯一答案**

Agent 可以用不同表述，也可以将一个需求拆为多个检索。检查当前信息需求是否正确、后续是否补齐，避免奖励照抄标准文案。

**(5) 正确状态字符串掩盖证据缺失**

Agent 声称 `ready_for_sql`，还需要检查依据是否齐全、有来源、无错误和阻断性缺口。无匹配任务声称 `insufficient_evidence` 也需要说明缺失内容并遵守停止规则。

**(6) 不适用、任务失败与评测失败混在一起**

没有 JOIN 的任务，Join Recall 为 N/A；需要 JOIN 却没找到是 0；响应证据缺失或评分器异常是评测错误。三者不能统一跳过，否则成绩会被虚增。

**(7) 只统计成功调用和成功样本成本**

失败、超时、重复调用也消耗时间与 Token。全量成本与成功样本成本分别报告，不能因为 Agent 提前放弃而判定优化有效。

**(8) 为了评测而泄露 Gold 或未来信息**

模拟规则、参考查询、后续工具响应和脚本用户回复不能一次性放进模型上下文。task 能读取 DatasetItem 不代表 Agent 应该看到全部字段。

**(9) 仅依赖单个 Observation 的托管 Judge**

一个工具 Observation 未必包含用户意图、历史依据、后续选择和最终交接。离线评测由 SDK evaluator 组装必要的完整证据再调用 Judge；线上监控则在目标 Observation 明确记录所需上下文，不能假定平台自动加载整条轨迹。

**(10) 版本与运行完成状态没有核对**

数据集更新、响应集调整和索引变更都会影响可比性。实验保存 Scores 后仍需检查样本与适用评分是否完整，存在评测错误时不得输出「通过」。
